## 2. Цель и границы

StudySpace — бесплатное Telegram Mini App для учёбы. Сохраняются пять вкладок: главная, расписание, задания, материалы, профиль. Стек: React/TypeScript/Vite/Tailwind, Hono/Cloudflare Workers, D1.

Ближайший результат — пилот расписания ИС-942:

1. Администратор выбирает конкретную неделю и фото общей таблицы нескольких групп.
2. Браузер находит/позволяет выделить ИС-942 и распознаёт текст локально.
3. Администратор проверяет и исправляет строки, сохраняет черновик.
4. Отдельно подтверждает публикацию.
5. Студент читает опубликованное расписание на неделю и сегодня.

Изменения по чётным/нечётным неделям и разовые замены хранятся как конкретная неделя `week_start` (понедельник), без повторяющихся шаблонов чётности. Часовой пояс — `Asia/Novosibirsk`. Подгруппы: `1`, `2`, `null` (общее занятие); пока показываются обе.

Ограничения продукта: бесплатные инструменты, отсутствие платных OCR API, исходное фото не отправляется на backend, публикация не происходит автоматически. Telegram initData проверяется сервером. Новые публичные туннели, удалённое развёртывание и публикацию данных не выполнять автоматически после паузы.

## 3. Что реализовано

### Backend и данные

- `database/migrations/0002_schedule.sql`: `schedule_weeks`, `lessons`, частичный уникальный индекс одной опубликованной версии для группы и недели.
- UUID недели передаётся строкой, не числом.
- Валидация понедельника, дат, часов, обязательных полей, подгруппы, размера тела и количества занятий.
- Все маршруты требуют проверенный Telegram-контекст; запись — серверную роль `admin`.
- Создание и изменение черновика; опубликованная версия не редактируется напрямую.
- Замена публикации выполняется атомарным D1 batch: прежняя версия архивируется. Повторный запрос публикации старого черновика не должен архивировать действующую неделю.
- Множественная вставка занятий через `json_each`, чтобы не раздувать число SQL-параметров.

| Маршрут | Назначение |
| --- | --- |
| `GET /api/schedule/week?week_start=YYYY-MM-DD` | `{ week: { id, week_start, status, lessons } \| null }` |
| `GET /api/schedule/today` | `{ date, lessons }` |
| `POST /api/schedule/drafts` | `{ week_start, lessons }` → `{ id }` |
| `PUT /api/schedule/drafts/:id` | обновление черновика |
| `POST /api/schedule/drafts/:id/publish` | отдельная публикация |

`Lesson`: `day_of_week`, `start_time`, `end_time|null`, `subject_name`, `classroom|null`, `teacher|null`, `subgroup`, `position`.

### Frontend

- Главная читает занятия на сегодня, вкладка расписания переключает недели и показывает опубликованные занятия по дням.
- Административный импорт встроен в существующую вкладку, без новой навигации.
- Редактор занятий, предупреждения пересечений, сохранение и отдельное подтверждение публикации.
- Сомнительные OCR-строки вынесены в список: «Перенести в редактор» / «Пропустить».
- Пока список проверки не разобран, кнопка сохранения отключена. Перенесённая строка с сомнительным временем имеет пустое начало: его нужно заполнить вручную.
- Перенесённые строки добавляются **в конец** редактора, а не сортируются по дню/часу. Это уже путало пользователя.
- В карточках проверки пока не отображаются отдельными полями часы/кабинет; одинаковые предметы разных пар трудно отличать. Возможная следующая UX-правка, но ещё не сделана.

- `prepare-ocr.mjs` копирует assets из npm-пакетов в `frontend/public/ocr`; запускается перед dev/build. Assets исключены из Git.
- В Telegram Desktop штатный file picker **не открылся**, в том числе после явного `showPicker`/`click`; системная причина не установлена.
- `PhotoInput.tsx`: русская кнопка выбора, вставка изображения через кнопку буфера и поле Ctrl+V, перетаскивание PNG/JPG. **Вставка реального фото через буфер сработала.** Остальные способы не считать полностью проверенными.
- Проверки файла: PNG/JPG, до 15 МБ, до 24 Мп, не менее 400 px по короткой стороне; перед работой максимальная сторона ограничивается 3000 px.
- Выбранная таблица физически обрезается, увеличивается до 3 раз с ограничением размера; длинные линии сетки удаляются; для области используется `PSM.SPARSE_TEXT`, `rotateAuto`. Для поиска на полном фото остаётся `PSM.AUTO`.
- `importModel.ts` объединяет фрагменты даты, использует даты внизу дневных блоков, сохраняет только однозначные границы. При пропуске даты не сдвигает следующие дни.
- Нечитаемые токены времени сохраняют место при образовании пар; слишком удалённые токены не связываются. Сомнительное время не подставляется в готовое занятие.
- Есть разворачиваемый исходный «Распознанный текст» для диагностики.

## 6. Точка остановки — сохранение черновика

Последнее сообщение пользователя: кнопка создания черновика «не сработала», во вкладках ничего не появилось. Пользователь попросил остановиться до дальнейших изменений. Затем отдельно поручил записать handoff.

При подготовке этого handoff выполнен только read-only запрос к локальной D1:

```sql
SELECT week_start, status, COUNT(*) AS versions
FROM schedule_weeks GROUP BY week_start, status;
```

Результат: **пустой список**. В текущей локальной базе нет ни сохранённых черновиков, ни опубликованных недель. Это подтверждает отсутствие сохранённых данных, но **не устанавливает причину**.

Что проверить первым после возобновления:

1. Было ли `review.length > 0`: сохранение тогда намеренно `disabled`.
2. Не оставлено ли пустое начало/предмет после переноса: клиент выбрасывает сообщение перед API-запросом.
3. Увидел ли пользователь сообщение: оно находится выше редактора и может оказаться вне экрана.
4. Отправлялся ли `POST /api/schedule/drafts`, HTTP-статус/ответ, действующая роль и initData. `apiFetch` пока показывает общий `API error N`, без подробностей валидации.
5. Если ответ успешен, появились ли строки в D1, сохранён ли `id` в UI и стало ли доступно отдельное подтверждение публикации.

Публичные вкладки по дизайну читают только **published**, а не draft. Отсутствие черновика в них само по себе не является ошибкой. При этом **отдельного списка и повторного открытия черновиков пока вообще нет**: состояние `draft`/редактора хранится в React, при обновлении страницы теряется. Backend GET/list черновиков не реализован. Это существенный пробел удобства/приёмки, а не подтверждение потери серверных данных.
